# Architecture

**Analysis Date:** 2026-02-03

## Pattern Overview

**Overall:** Hybrid monorepo with **Payload CMS** + **Next.js 16 App Router** + **tRPC backend** for an e-learning platform with digital product sales.

**Key Characteristics:**
- **Dual database systems**: Payload CMS (PostgreSQL with auto-schema push disabled) + Drizzle ORM (manual migrations)
- **Turborepo workspace orchestration** with shared packages for cart, types, UI, and API
- **Route groups** for clear separation: `(frontend)` public pages, `(on-poynt)` authenticated tools, `(payload)` CMS admin
- **Block-based content architecture** with reusable Payload blocks rendered as React components
- **Client-side cart state** with Zustand localStorage persistence
- **Stripe integration** via Payload plugin for product/price sync
- **AI-powered tools** (channel guide, marketing plan generator, decline responder) backed by OpenAI

## Layers

**Presentation/Frontend (`apps/web/app/(frontend)`):**
- Purpose: Public-facing e-learning marketplace
- Location: `apps/web/app/(frontend)/`
- Contains: Page routes, dynamic product/blog/service pages, block renderers
- Depends on: Payload CMS (via `getPayload()`), Zustand cart store, UI components
- Used by: Anonymous visitors, authenticated customers

**Application/Planner (`apps/web/app/(on-poynt)`):**
- Purpose: Authenticated AI-powered planning tools behind auth wall
- Location: `apps/web/app/(on-poynt)/on-poynt/`
- Contains: Tool pages (channel guide, marketing plan, yearly planner, decline generator), settings, workspace management
- Depends on: tRPC API, Better Auth, Drizzle DB, OpenAI API
- Used by: Authenticated users with workspace profiles

**Payload Admin (`apps/web/app/(payload)`):**
- Purpose: CMS admin interface for content management
- Location: `apps/web/app/(payload)/`
- Contains: Payload CMS admin panel (auto-generated by Payload)
- Depends on: Payload collections/globals, PostgreSQL
- Used by: Content editors and admins

**API Layer:**
- **tRPC Router** (`packages/planner-api/`): Type-safe backend procedures for planner tools
  - Location: `packages/planner-api/root.ts` aggregates all routers
  - Routers: `aiRouter`, `workspaceRouter`, `industryRouter`, `adminRouter`, `toolResultRouter`, `marketingPlanProgressRouter`, `declineFeedbackRouter`
  - Pattern: Procedures use validators from `@poynt/planner-validators` and database queries via Drizzle

- **REST/Webhook Endpoints** (`apps/web/app/api/`):
  - `/api/checkout` - POST: Validates cart items, creates Stripe checkout session
  - `/api/webhooks/*` - Stripe webhooks, newsletter subscription handling

**Data/State Layer:**
- **Payload CMS Collections** (`apps/web/src/collections/`):
  - `Users`: Auth with roles (admin/customer), Stripe customer ID
  - `Products`: Synced to Stripe via plugin, includes type (course/PDF/bundle), pricing, gallery
  - `Orders`: Purchase records with Stripe payment IDs
  - `Pages`: Dynamic pages with block layout builder
  - `BlogPosts`, `Podcasts`, `Services`: Content collections with block support

- **Planner Database** (`packages/planner-db/schema/`):
  - `auth`: User profiles with email, auth tokens (separate from Payload)
  - `workspace`: Workspace records, memberships, roles
  - `admin`: Industries, prompt configurations
  - **Managed via Drizzle ORM** with manual migrations (isolated from Payload schema)

- **Client-Side State** (`packages/cart/`):
  - Zustand store with localStorage persistence (key: "poynt-cart")
  - Constraint: Digital products limited to 1 per item in cart

**Shared Infrastructure:**
- **UI Components** (`packages/ui/`): Radix UI + Tailwind components (button, card, dialog, form, etc.)
- **Type Definitions** (`packages/types/`): Shared TypeScript interfaces
- **Email Service** (`packages/email/`): Resend integration (not yet implemented)
- **Stripe Wrapper** (`packages/stripe/`): SDK client with configuration
- **Validators** (`packages/planner-validators/`): Zod schemas for form validation and tRPC input/output
- **Authentication** (`packages/planner-auth/`): Better Auth integration (separate from Payload auth)

## Data Flow

**Customer Purchase Flow:**

1. **Browse Products** (`(frontend)/produkter/[slug]`)
   - Query Payload via `getPayload()` for product details
   - Render product card with Add to Cart button

2. **Add to Cart**
   - Client-side `useCart()` (Zustand) adds item to store
   - Persisted to localStorage as "poynt-cart"

3. **Checkout** (`/handlekurv` → POST `/api/checkout`)
   - Validate user auth (Payload auth required)
   - Fetch cart items from Zustand state
   - Validate products exist and prices match database
   - Create Stripe checkout session with line items (price IDs)
   - Return session URL to redirect user

4. **Payment** (Stripe.js)
   - User completes payment in Stripe-hosted checkout
   - Stripe webhook hits `/api/webhooks/stripe` with session details

5. **Confirmation** (`/kvittering?session_id=...`)
   - Query Payload for order records
   - Display receipt and access information

**AI Tool Flow (e.g., Channel Guide):**

1. **User Loads Tool** (`(on-poynt)/verktoy/kanalveileder`)
   - Server-side page fetches workspace + industries from Planner DB via tRPC
   - Render `channel-guide-client.tsx` with initial state

2. **Submit Questionnaire**
   - Client sends form data to tRPC `ai.channelGuide()` procedure
   - Procedure validates input with `channelGuideRequestSchema`
   - Queries `plannerIndustry` table for industry context

3. **AI Generation**
   - OpenAI API called with system prompt + validated user input
   - Returns `ChannelGuideResponse` (channels array with match percentages and reasoning)

4. **Save Result**
   - Client calls `toolResult.create()` tRPC procedure
   - Stores result in `tool_results` table with workspace ID
   - Result persisted and queryable by workspace

**State Management:**

- **Server-side**: Payload (CMS content), Drizzle (planner data)
- **Client-side**: Zustand (cart), React Server Components (metadata fetching), React state (form inputs)
- **Session**: Payload auth context (`payload.auth({ headers })`)
- **Workspace context**: tRPC context includes authenticated user + workspace association

## Key Abstractions

**Block System** (`src/blocks/`, `components/blocks/`):**
- Purpose: Define Payload schema blocks → render as React components
- Examples:
  - `src/blocks/hero.ts` - Payload config (admin UI)
  - `components/blocks/hero-block.tsx` - React render component
  - Others: content, CTA, media, testimonials, product archive, services archive, podcast archive
- Pattern: Block config exported from `src/blocks/`, registered in `payload.config.ts`, rendered by `RenderBlocks` component

**Collections & Globals** (`src/collections/`, `src/globals/`):**
- Purpose: Payload schema definitions (collections are multi-document, globals are singletons)
- Collections: Users, Products, Orders, Pages, BlogPosts, Podcasts, Services, CourseContent, Categories, Media
- Globals: SiteSettings, Header, Footer, Homepage, BlogPage, ProductsPage, ServicesPage, ProductSettings, PodcastPage
- Pattern: Each exported as `CollectionConfig` or `GlobalConfig`, registered in `payload.config.ts`

**Stripe Sync Plugin:**
- Purpose: Automatically sync Products collection to Stripe
- Mechanism: Product hook `afterChange` creates Stripe product + price objects, stores IDs on product doc
- Sync fields: Product name → Stripe product name, price → Stripe price (in NOK øre)

**tRPC Routers** (`packages/planner-api/routers/`):**
- Purpose: Type-safe API procedures grouped by domain
- Pattern: Each router exports mutations/queries via `publicProcedure`
- Examples: `ai.channelGuide()`, `workspace.getWorkspaces()`, `admin.getIndustries()`
- Validators: Input validated with Zod schemas from `@poynt/planner-validators`

## Entry Points

**Application Start:**
- Location: `apps/web/next.config.mjs` with Payload integration via `withPayload()`
- Triggers: Server startup (`bun run dev`), Next.js builds app with Payload CMS admin embedded

**Frontend Public Pages:**
- Location: `apps/web/app/(frontend)/page.tsx` (homepage)
- Sub-routes: `/produkter/[slug]`, `/blogg`, `/post/[slug]`, `/podkast/[slug]`, `/tjenester/[slug]`, `/[...slug]` (catch-all dynamic pages)
- Responsibilities: Fetch content from Payload, render blocks, handle SEO metadata

**Authenticated Planner Pages:**
- Location: `apps/web/app/(on-poynt)/on-poynt/(app)/`
- Requires: Better Auth middleware enforces authentication
- Sub-pages: `/oversikt` (overview), `/verktoy/*` (tool pages), `/innstillinger/*` (settings)
- Responsibilities: Fetch workspace data, render tool UI, handle tRPC API calls

**API Routes:**
- Location: `apps/web/app/api/`
- `/checkout` - POST: Handle cart checkout, create Stripe session
- `/webhooks/stripe` - POST: Handle Stripe payment webhooks
- `/newsletter` - POST: Handle newsletter subscription (Resend)

**Payload Admin:**
- Location: `apps/web/app/(payload)/`
- Rendered by: Payload's `@payloadcms/next` integration (auto-managed)
- Path: `/admin` (hardcoded in Payload config)

## Error Handling

**Strategy:** Try-catch in API routes with error logging, Payload hooks log to `req.payload.logger`, tRPC procedures throw typed errors.

**Patterns:**

- **API Routes** (`app/api/checkout/route.ts`):
  ```typescript
  try {
    // Business logic
    return NextResponse.json({ url: session.url });
  } catch (error) {
    req.payload.logger.error(`Error message: ${error}`);
    return NextResponse.json(
      { error: error instanceof Error ? error.message : "Generic error" },
      { status: 500 }
    );
  }
  ```

- **Payload Hooks** (`src/collections/products.ts`):
  ```typescript
  hooks: {
    afterChange: [
      async ({ doc, req }) => {
        try {
          // Create Stripe price
        } catch (error) {
          req.payload.logger.error(`Failed to create price: ${error}`);
        }
      }
    ]
  }
  ```

- **tRPC Procedures** (`packages/planner-api/routers/ai.ts`):
  ```typescript
  export const aiRouter = router({
    channelGuide: publicProcedure
      .input(channelGuideRequestSchema)
      .mutation(async ({ input }) => {
        // Input validated automatically by Zod
        // Throw errors naturally, tRPC serializes to response
      })
  });
  ```

- **Client Error Handling** (`components/blocks/form-block.tsx`):
  - Form validation via React Hook Form + Zod
  - Display field-level errors below inputs
  - Show toast notifications for submission errors

## Cross-Cutting Concerns

**Logging:**
- Payload: Uses `req.payload.logger.error()` / `.warn()` / `.info()`
- Frontend: Console logs for debugging (no centralized logging for client errors)
- tRPC: Implicit via error responses

**Validation:**
- **Payload Collections**: Field-level validation (`required`, `unique`, `type` enforcement)
- **tRPC Input**: Zod schemas validate mutation/query inputs (e.g., `channelGuideRequestSchema`)
- **Forms**: React Hook Form + Zod schemas on client (e.g., ProductFilter)
- **Stripe Checkout**: Validate products exist, are active, have Stripe price IDs

**Authentication:**
- **Payload Auth**: Email/password auth built-in (`auth: true` on Users collection)
  - Session stored in httpOnly cookie
  - Retrieved via `payload.auth({ headers: req.headers })`

- **Better Auth**: Separate auth system for Planner app (users, sessions in separate DB)
  - Handles OAuth setup for future integrations
  - Session middleware in `(on-poynt)` layout

- **Authorization**: Role-based checks
  - Payload: Admin role required for CMS admin access
  - Planner: Workspace membership checked in tRPC context

**Environment Configuration:**
- Global env vars in `turbo.json`: `DATABASE_URI`, `PAYLOAD_SECRET`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `OPENAI_API_KEY`, `RESEND_API_KEY`
- Payload URL: `NEXT_PUBLIC_URL` or `http://localhost:3000`
- Vercel Blob: `BLOB_READ_WRITE_TOKEN` (optional, enables CDN)
